# CI and public delivery: primary-source evidence

2026-10-29. Scope: research evidence for the parent investigation. OpenPost timing figures below are supplied by the parent from its trace, not independently reproduced here. No performance claims from vendors are estimates of OpenPost savings.

## Observed baseline and questions

The supplied v7.34.2 trace reports 50m28s from tag to public changelog, including a 12m22s Pages deployment. Initialization and clone took 19s, first install 46.5s, second install 1.1s, docs inputs 120.71s, docs build 122.73s, and marketing 467.05s. Marketing and docs ran concurrently in separate Turbo invocations, so these durations cannot be added. Two PostHog upload phases contain many batches. Their exact upload-only durations require trace analysis. Composition took 0.29s, asset upload 55.28s within a roughly 72s deployment stage. Turbo reported remote cache disabled and 8/8 misses; shared tasks appeared in both invocations. The browser job took 23m59s with about five minutes setup and 7m51s queue. These are observations, not proof any single component is entirely avoidable.

A changelog edit triggers a full site build today, per the supplied architecture. Correct publication, artifact integrity, route and symbolication checks remain necessary; their current placement and repeated work are choices to measure. Extra parallel PR matrix jobs can compete with artifact producers and increase queue time.

## Industry mechanisms

- **Google/Bazel:** explicitly declared action inputs, commands and environment yield action keys; an action cache and content-addressed store share reproducible outputs. Network transfer, undeclared inputs and cache poisoning/trust are real constraints. Compare input hashes and warm/cold builds on the existing Turbo graph first, including provenance variables; this does not justify a Bazel rewrite. [Bazel remote caching](https://bazel.build/versions/7.1.0/remote/caching), [Google distributed builds](https://bazel.build/versions/7.7.0/basics/distributed-builds).
- **Meta/Buck2:** a single incremental dependency graph invalidates affected nodes and schedules work with greater parallelism; language rules, hermeticity and remote infrastructure still cost engineering effort. The applicable idea is one coordinated graph and correctly declared shared outputs, not migration to Buck2. [Meta's Buck2 design](https://engineering.fb.com/2023/04/06/open-source/buck2-open-source-large-scale-build-system/).
- **Meta/test selection:** predictive selection learns from historical change and test outcomes; its separate flakiness system tracks reliability over time and assigns ownership. For OpenPost, first shadow a conservative dependency selector against exhaustive runs and measure missed failures; retain full release qualification and do not silently treat flakes as passing. Meta's scale and data do not transfer automatically. [Predictive selection](https://engineering.fb.com/2018/11/21/developer-tools/predictive-test-selection/), [flakiness measurement](https://engineering.fb.com/2020/12/10/developer-tools/probabilistic-flakiness/).
- **GitHub merge queue:** checks run against the target branch plus preceding queued changes, with configurable build concurrency and batching. Required workflows must handle `merge_group`; a queue can consume runners and add latency, so measure merge contention before adoption. [GitHub merge queue](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue?tool=webui).
- **Cloudflare prebuilt delivery:** Direct Upload accepts prebuilt assets; a Git-integrated Pages project can disable automatic deployments and use Wrangler, although its project integration type cannot be switched. This enables a build-once/promote experiment, subject to exact commit/artifact provenance, checksums, configuration, safe rollout and live verification. [Direct Upload](https://developers.cloudflare.com/pages/get-started/direct-upload/), [Git integration](https://developers.cloudflare.com/pages/configuration/git-integration/). Pages documents unique, atomic preview URLs, but that does not alone prove production alias propagation or cross-deployment atomicity. [Preview deployments](https://developers.cloudflare.com/pages/configuration/preview-deployments/).

Uber’s published Jazelle repository documents incremental, cacheable JavaScript monorepo builds and dependency-ordered build execution. This is evidence for graph-based reuse, not an estimate of OpenPost savings or proof of Uber’s entire internal CI configuration. [Uber Jazelle source and README](https://github.com/uber-web/jazelle).

## Pages and source maps

Pages Git builds normally trigger for any repository change. Watch paths filter pushes, with documented bypasses for empty pushes, 3,000+ files or 20+ commits; include the complete transitive public-site inputs, including changelog, shared packages and generated inputs. [Watch paths](https://developers.cloudflare.com/pages/configuration/build-watch-paths/). Cloudflare says Pages incremental builds are unsupported; this does not establish the behavior of every package cache or external Turbo cache. [Known issues](https://developers.cloudflare.com/pages/platform/known-issues/).

PostHog documents that minified stack traces need matching source maps and supports upload during builds; releases can associate repository and version context. [PostHog stack traces](https://posthog.com/docs/error-tracking/stack-traces/). Its own integration checklist warns that injected chunk IDs must appear in deployed bundles and maps may accidentally ship publicly, and recommends production-build verification. [PostHog integration checklist](https://posthog.com/handbook/wizard-and-docs/wizard-edge-cases). A static adapter produces a static site, but this alone does not prove which OpenPost server bundles run at build time or whether build failures need server symbolication. [Svelte packages](https://svelte.dev/packages). Candidate: omit server-map upload only after inspecting deployed output and operational error paths, while retaining client maps privately and proving a deployed browser exception resolves. Verify privacy and access controls for maps containing source.

**Unresolved:** The cited docs do not establish deterministic debug IDs, upload deduplication, or safe asynchronous upload semantics for the exact installed plugin/CLI. Inspect its pinned implementation and verify matching injected IDs, release association, retries, ordering and delayed exceptions before changing the boundary. An asynchronous upload may create a period of unsymbolicated errors or lose maps on failure; test whether PostHog reprocesses early events rather than assuming it does.

## Experiments for the parent decision trail

1. Baseline a single coordinated Turbo invocation against the two-invocation trace: compare task hashes, outputs, wall time and public-site content; preserve provenance. Keep only if outputs and route checks agree.
2. Measure source-map injection and upload separately for client and server. Compare hashes and IDs across identical builds, test duplicate uploads and release linking, then trigger a real deployed browser exception and check source-map privacy. Treat unproven async recovery as inconclusive.
3. Cache docs inputs and shared tasks using fully declared inputs. Compare cold and warm builds and intentionally change each relevant input; unknown dependencies fail closed. Measure transfer and cache trust costs.
4. Prototype artifact promotion with a manifest of revision, configuration and digests; verify the served revision, changelog, redirects and symbolication, and test rollback. Do not substitute tag artifacts for the later changelog commit without proving their contents match.
5. Record runner queue and producer critical path before changing matrix concurrency; shadow affected-test selection against exhaustive checks, record misses and retain release coverage.

Each experiment is a reversible hypothesis, judged against its baseline and observable artifact; results remain **NOT VERIFIED** until run. The parent owns the canonical design and decision TSV.
