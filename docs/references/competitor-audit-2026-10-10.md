# Weekly competitor audit, 3 to 10 October 2026

Checked on 10 October 2026 against primary GitHub APIs, refreshed source checkouts, provider documentation, and OpenPost revision [`be436b60ea57870821018c3dd041b7a0abc156b1`](https://github.com/getopenpost/openpost/tree/be436b60ea57870821018c3dd041b7a0abc156b1). Findings below describe that baseline. Implementation and verification belong to the changes and tests that follow this audit, rather than an assertion that the baseline already contains them.

The supplied audit correctly identifies the most valuable work: provider identity, processing checkpoints, and recovery guidance. This pass also found a billing subscription-identity risk and missing Google session-policy guidance. YouTube already retains an accepted video ID and link when later finalization fails. It confirmed an additional TikTok false-success path when processing polls run out.

## Scope and method

The original seven-repository list was unavailable. This audit uses the four named competitors, plus Mixpost and Socioboard as relevant public schedulers, and OpenPost as the comparison baseline. This is an explicitly chosen scope, not a reconstruction of the original list.

Commit inventories use GitHub's committer-time range `2026-10-03T00:00:00Z` through `2026-10-11T00:00:00Z`, limited by what existed when checked. Counts include merges and commits brought in by merged branches. They measure activity, not independent features. Default branches, recent releases, the latest 100 updated pull requests and issues per repository, and an additional 100 Postiz pull requests were checked. Selected merged and open work received source-level review. TryPost #390's 73-commit sequence was inspected, including its reversions. This does not claim every line of every commit was reviewed.

All six competitor checkouts were refreshed or cloned under the ignored `docs/references/` directory. Existing clean Postiz, TryPost and Shoutrrr checkouts were updated with `pull --ff-only`; their shallow histories needed deepening before Git could prove ancestry. New paths use local Git excludes. Socioboard's old default checkout has case-colliding paths on macOS, so its active `6.0` source was reviewed in a separate shallow checkout. No competitor source was transplanted.

### Additional findings from this pass

**P1, cancellation of an old billing subscription must not replace the current subscription.** PostHive's [8 October fix `7389d67ff8`](https://github.com/AstaBlackClove/posthive/commit/7389d67ff822ee896d187e24d79abd820608fada) ignores a cancellation event when its subscription ID differs from the active workspace subscription. OpenPost's `services/billing/service.go` correctly fetches current Paddle objects and orders snapshots by `provider_updated_at`, but its `upsertSubscription()` conflicts on `organization_id` and overwrites `provider_subscription_id`. A later update to a former subscription can have a newer timestamp than the current active subscription. Timestamp ordering alone cannot prove ownership. Add a regression for active subscription B followed by a newer cancellation of old subscription A, while retaining legitimate replacement-subscription admission and same-subscription updates. This is a code-confirmed missing identity boundary, not a reproduced live charge or outage.

**P2, preserve Google session-control subtypes.** Postiz's [#1884, merged 9 October](https://github.com/gitroomhq/postiz-app/pull/1884) adds guidance for `invalid_rapt`. At the baseline, OpenPost's `platform/errors.go` discards Google's `error_subtype`. Google's official documentation classifies `invalid_grant` with `error_subtype=invalid_rapt` as session-control expiry and requires restarting authorization. Its documented scope is GCP organization session policies and OAuth applications requiring Cloud Platform scope, not every YouTube account. Preserve the structured subtype when received and offer reconnect plus policy guidance. Do not classify it as a transient outage, infer it from arbitrary text, or promise trusted-app settings always fix it. [Google OAuth session-control documentation](https://developers.google.com/identity/protocols/oauth2#expiration).

**Covered, YouTube video identity after thumbnail failure.** Postiz's [open #2066](https://github.com/gitroomhq/postiz-app/pull/2066) retains an accepted video ID and URL after thumbnail failure. OpenPost already does this in `saveRenditionMediaDelivery()`: the same transaction persists `ProviderMediaID` and the Rendition's external ID/watch URL before thumbnail/caption finalization. The initial assessment of a missing visible identity was incorrect. Preserve the existing behavior and regression coverage. [Baseline persistence helper](https://github.com/getopenpost/openpost/blob/be436b60ea57870821018c3dd041b7a0abc156b1/apps/server/internal/services/publisher/publisher.go#L1587).

**P2, bounded X reads need an honest cost model.** TryPost #399's approximately $16.30/day before and $2.10/day after are its own modeled production costs, not an OpenPost benchmark. Its useful mechanisms are entitlement gates, a one-hour first read, sparse age-based X reads, and avoiding redundant discovery. OpenPost already avoids X discovery and uses durable analytics snapshots and backoff. Prefer explicit accounting and provider-specific cadence over copying TryPost's analytics architecture. X currently documents $0.005 per returned Post and $0.010 per returned User, with deduplication within a UTC day described as a soft guarantee. Owned-read pricing applies only when the authenticated user also owns the developer app, so Hosted customer analytics cannot assume that discount. [X pricing checked 10 October 2026](https://docs.x.com/x-api/getting-started/pricing).

### Meta lifecycle evidence and limits

Meta's official Facebook collection shows `uploading_phase=complete` alongside `processing_phase=not_started` and `video_status=processing`. Its maintained sample confirms successful finish is only an acknowledgement and checks `publishing_phase.status=complete` before reporting publication. These support separate transfer, processing and publication states. [Meta Facebook collection](https://www.postman.com/meta/facebook/documentation/r56bjfd/facebook-api?entity=request-23987686-a9ea20fe-d410-4804-8bbe-5cc5985e9443), [official sample pinned at `7bf98f94e7`](https://github.com/fbsamples/reels_publishing_apis/blob/7bf98f94e75d841ecc9612c0061881d1d713c6bd/fb_reels_publishing_api_sample/index.js#L320). `debug_info.retriable` is evidenced by TryPost's source and fixtures; an official definition or upload replay guarantee was not found. Meta's developer pages returned 429 or were unavailable. Preserve the existing session and reconcile status after ambiguous responses; the flag alone does not prove blind replay safe.

Meta's official Instagram example waits for confirmed `FINISHED`, publishes the container, stores the returned published-media ID, then requests that ID's `permalink`. Container identity and published-media identity are distinct. [Official sample](https://github.com/fbsamples/reels_publishing_apis/blob/7bf98f94e75d841ecc9612c0061881d1d713c6bd/insta_reels_publishing_api_sample/index.js#L378), [Meta container-status request](https://www.postman.com/meta/instagram/request/munmruq/get-ig-container-status). Deferring a native discovery near an unresolved publication is an OpenPost safety policy informed by TryPost #394, not a documented Meta matching rule. No official caption/time/permalink heuristic guarantees authorship. Keep exact confirmed IDs authoritative, preserve confirmed IDs when optional permalink reads fail, and defer ambiguous classification with bounded account/type/time scope rather than invent an alias.

### X upload retry evidence and limits

Current X documentation defines an upload session ID, `segment_index`, processing states and `expires_after_secs`. It does not explicitly guarantee that replaying an APPEND with the same ID/index is idempotent. Preserve accepted segment progress, but keep an APPEND with a lost response reconcile-only unless a documented replay guarantee becomes available. A STATUS read can inspect the existing media ID after a lost FINALIZE response; unknown status must remain ambiguous rather than complete successfully. Do not infer that a pre-finalization STATUS response will prove the last chunk arrived. OpenPost currently uses the v1 upload endpoint, and the old v1 documentation links redirect to the platform overview, so the current v2 response contract is evidence for the design rather than proof that every legacy response is identical. [APPEND](https://docs.x.com/x-api/media/append-media-upload), [INIT](https://docs.x.com/x-api/media/initialize-media-upload), [FINALIZE](https://docs.x.com/x-api/media/finalize-media-upload), [STATUS](https://docs.x.com/x-api/media/get-media-upload-status).
