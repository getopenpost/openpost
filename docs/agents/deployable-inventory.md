# Deployable Inventory

Read this inventory before changing runtime configuration, release workflows, or revision evidence. A successful build proves only that an artifact was built. Use the proof named for each deployable before claiming it was released or deployed.

| Deployable                  | Configuration owner                                                                                                                                                                                                                                                                                  | Release path                                                                                                                                                                                                                                                                     | Revision proof                                                                                                                                                                                                                                                                                 |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Server and embedded web app | Bootstrap and data-plane values come from environment variables or their `_FILE` forms through `backend/internal/config/config.go`. Admin-managed settings are declared in `backend/internal/config/managed.go` and stored through `backend/internal/services/instancesettings/service.go`.          | Candidate CI builds `docker/Dockerfile` once as `ghcr.io/<repository>:sha-<SHA>` and records `release-manifest.json` plus `openpost-image-evidence.json`. The tag workflow promotes that digest, deploys it, and uploads `openpost-server-*` binaries built from the tagged SHA. | `scripts/image-evidence.mjs` binds the candidate digest to the full SHA. `scripts/verify-image-release-manifest.sh` verifies the image. Production must report the tag and full SHA from `/api/v1/version`, with `/api/v1/ready` ready. Standalone server binaries embed the same tag and SHA. |
| Marketing site              | Source and build configuration live under `marketing-site/`, including `marketing-site/vite.config.ts`. The external runtime owner is the Cloudflare Pages project `openpost-marketing`.                                                                                                             | The Pages Git integration builds clean `main` to `marketing-site/dist`. CI retains a build artifact for verification but does not deploy it.                                                                                                                                     | Run the marketing build, then `scripts/public-deployment-proof.mjs prove` as described in `docs/operations/cloudflare-edge-plan.md`. It requires the local full SHA, the Pages deployment full SHA, and the live host to agree.                                                                |
| Documentation site          | Source and build configuration live under `docs-site/`, including `docs-site/.vitepress/config.ts`. The external runtime owner is the Cloudflare Pages project `openpost-docs`.                                                                                                                      | The Pages Git integration builds clean `main` to `docs-site/.vitepress/dist`. CI retains a build artifact for verification but does not deploy it.                                                                                                                               | Run the documentation build, then the same public deployment proof. It requires the local full SHA, the Pages deployment full SHA, and the live host to agree.                                                                                                                                 |
| Android app                 | Release name and code live in `mobile/app.json` and `mobile/package.json`. Native persistence belongs in `mobile/app.json` or `mobile/plugins/`. Per-install server and token state live in `mobile/src/lib/server.ts` and `mobile/src/lib/api/token-store.ts`. GitHub owns release signing secrets. | Candidate CI checks monotonic identity, builds the unsigned APK once, and records its SHA-256 and candidate manifest. The tag workflow verifies that input, signs it, and uploads `openpost-app-android.apk` plus `openpost-app-android-release.json`.                           | `scripts/mobile-release.mjs` binds version, Android version code, full SHA, and APK SHA-256 in both manifests. The release workflow verifies the candidate before signing.                                                                                                                     |
| CLI and MCP proxy           | Profiles and endpoint precedence live in `cli/internal/config/config.go`. Tokens live behind `cli/internal/auth/token_store.go`, never in the profile file.                                                                                                                                          | The tag workflow builds `openpost-cli-*` and `openpost-mcp-*` for the release matrix and uploads them to the GitHub release.                                                                                                                                                     | The binaries embed and print the release tag. The GitHub release tag identifies the source SHA, but the CLI and MCP binaries do not independently embed the full SHA or publish a checksum manifest. Do not claim stronger executable-level revision proof.                                    |
| n8n package                 | Package identity and version live in `packages/n8n-nodes-openpost/package.json`. User-entered endpoint and token fields live in `packages/n8n-nodes-openpost/credentials/OpenPostApi.credentials.ts`. npm trusted-publisher configuration is external.                                               | After the exact server revision is live, the tag workflow packs and publishes `@getopenpost/n8n-nodes-openpost` through trusted publishing. Follow `docs/agents/n8n-package-release.md`.                                                                                         | `scripts/n8n-package-release.mjs` matches the packed tarball integrity to npm. `scripts/verify-published-n8n-package.mjs` checks registry integrity, npm signatures, and a clean install. npm provenance records the workflow source. The package SemVer is independent of the app tag.        |

Keep external deployment records outside the repository. Do not put Cloudflare responses, credentials, signing material, or operator evidence in Git.
