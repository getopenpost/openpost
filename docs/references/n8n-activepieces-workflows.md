## What should guide the next design discussion

The main choice is the executable document model. n8n stores a general graph with typed connections and streams of items. Activepieces stores a structured program with a trigger, a next step, and explicit branch and loop bodies. Both render a canvas, but those canvases expose different programming models. Svelte Flow can draw either; it does not make this decision for OpenPost.

My recommendation is to evaluate a structured executable model first, with stable step IDs, explicit branches and bounded loops, and a canvas as one view of it. The proposed source-to-draft, approval, scheduling and follow-up examples fit this model. If a representative workflow needs independent parallel branches and joins, specify those constructs explicitly. This is a recommendation to test, not a decision to restrict the product permanently.

n8n is the stronger reference here for data inspection, expressions, connector configuration, graph editing and partial execution. Activepieces is the clearer reference for an action SDK, structured editing operations, and persistent waitpoints. Neither should be treated as proof that retrying a failed step is safe for social publishing. OpenPost's existing publication, scheduling and provider-write services remain the owners of those effects.

## n8n editor, from document to interaction

### The canvas is a projection of the workflow

The Vue editor uses Pinia stores and Vue Flow. `Canvas.vue` receives projected nodes and edges and sets `apply-changes="false"`. It emits connection, drag and selection events rather than allowing the drawing library to become the authoritative workflow store. `useCanvasMapping` joins document state, connector metadata, validation and execution state into the shape Vue Flow renders. Custom node and edge components supply the product behavior. [Canvas component](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/frontend/editor-ui/src/features/workflows/canvas/components/Canvas.vue#L1899-L1938), [canvas mapping](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/frontend/editor-ui/src/features/workflows/canvas/composables/useCanvasMapping.ts#L40-L217).

This separation is worth adopting. A node status event should update a run overlay. It should not dirty the saved workflow. A selection rectangle or collapsed group should not define runtime behavior. The chosen canvas library's object format should remain an adapter format.

The document store composes owners for nodes, connections, settings, pins, versions, permissions, viewport and graph traversal. Runtime state has a separate store. The render adapter combines them using per-node computed entries and explicit scope disposal. The catalog uses a `shallowRef` to avoid making thousands of nested metadata objects reactive. These are concrete responses to editor size and update fan-out, not evidence of a particular frame rate. [Document store](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/frontend/editor-ui/src/app/stores/workflowDocument.store.ts#L1-L47), [render entry lifecycle](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/frontend/editor-ui/src/app/stores/workflowDocument/useWorkflowDocumentRenderData.ts#L60-L106), [entry reconciliation and disposal](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/frontend/editor-ui/src/app/stores/workflowDocument/useWorkflowDocumentRenderData.ts#L376-L455), [catalog storage](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/frontend/editor-ui/src/app/stores/nodeTypes.store.ts#L44-L49).

### Graph editing is a semantic command layer

`useCanvasOperations` owns adding, deleting, renaming, moving and connecting nodes, importing workflows, pinning outputs, grouping and duplication. It records commands in a bounded undo/redo store, with bulk commands for one multi-node interaction. The history limit is 100 entries. This is distinct from saved workflow versions and execution history. [Operations](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/frontend/editor-ui/src/app/composables/useCanvasOperations.ts#L338-L484), [history store](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/frontend/editor-ui/src/app/stores/history.store.ts#L1-L89).

There is a useful warning in node renaming. n8n has node IDs, but connections, expressions and much run data also address nodes by name. `renameNode` clones the workflow, rewrites references, changes execution-state keys, and updates the active node. The shared workflow class recursively rewrites expression strings and selected code/HTML fields. OpenPost can avoid this compatibility burden by making references use immutable IDs from the beginning and keeping labels cosmetic. [Editor rename](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/frontend/editor-ui/src/app/composables/useCanvasOperations.ts#L497-L558), [shared rename implementation](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/workflow/src/workflow.ts#L334-L455).

### Node search comes from the connector catalog

The node-types store resolves descriptions by type and version. Its action generator turns a node's resource and operation choices into searchable actions. Choosing an action therefore creates a configured node; it need not select a wholly different executor. The generator accounts for version-specific visibility conditions and has exceptions for unusual connectors. [Type/version lookup](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/frontend/editor-ui/src/app/stores/nodeTypes.store.ts#L97-L154), [action generation](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/frontend/editor-ui/src/features/shared/nodeCreator/composables/useActionsGeneration.ts#L114-L175).

Catalog loading also has layers. Full descriptions for selected node versions can come from a worker-owned local database or REST, with REST used for translated descriptions. Resource locator results, property options, resource-mapper fields and parameter actions have separate API calls. A searchable catalog is therefore only the first part of a connector system. [Metadata loading and dynamic requests](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/frontend/editor-ui/src/app/stores/nodeTypes.store.ts#L348-L472).

For OpenPost, search should expose outcomes such as Create draft, Schedule post and Reply to comment. Those entries can share a connector and service implementation while retaining distinct effect and permission contracts. A logo count would conceal the actual work in account-aware forms and useful operation descriptions.

### Configuration forms combine metadata and specialized controls

`ParameterInput` chooses controls from `INodeProperties`: ordinary values, options, credentials, resource locators, workflow selectors, JSON, code, dates and other specialized editors. Collections and filters have their own components. The node-details view arranges input data, configuration and output data together. This is much richer than putting every node through a generic JSON Schema form. [Parameter control owner](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/frontend/editor-ui/src/features/ndv/parameters/components/ParameterInput.vue#L1576-L1645), [node-details layout](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/frontend/editor-ui/src/features/ndv/shared/views/NodeDetailsView.vue#L796-L930).

Dynamic options are real server operations. `loadRemoteParameterOptions` resolves dependency values, sends node type/version, property path, credential references, project and workflow identity, and displays loading errors. A spreadsheet selector depends on a connection; its column choices depend on the selected sheet. That dependency graph needs invalidation, loading, authorization and stale-response handling. [Dynamic option request](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/frontend/editor-ui/src/features/ndv/parameters/components/ParameterInput.vue#L897-L950).

The practical lesson is to define a modest shared property vocabulary and allow custom editors for OpenPost publications, media and account-resolved provider settings. Do not duplicate the composer model inside a workflow-specific form system. Keep provider credentials on the server even when populating configuration choices.

### Data mapping and inspection are central to authoring

Dragging a field creates an expression. Immediate upstream data can become `$json`; a more distant source becomes a named-node expression with item linking. The mapping utility escapes field names and handles resource locators and property-path fields. These details let a user select a value without learning all the expression syntax. [Mapping utilities](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/frontend/editor-ui/src/app/utils/mappingUtils.ts#L15-L123).

The data inspector derives a browsable schema from execution samples and also accepts declared JSON Schema. For object arrays it can combine keys across samples. This improves discovery, but observed fields are not proof that every future item has them. OpenPost should distinguish a declared output contract, an observed example, an absent optional value and a missing required value. [Sample and declared schemas](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/frontend/editor-ui/src/app/composables/useDataSchema.ts#L35-L176).

Expressions use CodeMirror with syntax-tree segments, autocomplete and resolved previews. Segment resolution is asynchronous; a generation counter discards stale results, and changes and preview evaluation are debounced separately. OpenPost should copy the interaction principle: show the source and current resolved value together, with the selected sample and iteration visible. A Go expression runtime would need shared semantics or server-backed previews, rather than a second evaluator with slightly different coercions. [Expression editor](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/frontend/editor-ui/src/features/shared/editors/composables/useExpressionEditor.ts#L123-L214).

The node-details view tracks input and output run indexes and lets them be linked or inspected separately. A node can execute repeatedly; one green badge and one JSON object are insufficient for loops, retries and branches. [Run selection](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/frontend/editor-ui/src/features/ndv/shared/views/NodeDetailsView.vue#L249-L312), [input/output linking](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/frontend/editor-ui/src/features/ndv/shared/views/NodeDetailsView.vue#L461-L495).

### Saving, publishing and running are separate operations

Autosave is serialized through a pending-save promise. A save captures the dirty counter, sends the document's version and expected checksum, rejects a wrong-document save, and only clears dirty state if no new edit arrived. A 409 takes the conflict path. Debounced autosave schedules another save when edits arrived during the request. This handles common data-loss races that a simple debounce does not. [Save implementation](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/frontend/editor-ui/src/app/composables/useWorkflowSaving.ts#L394-L532), [autosave lifecycle](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/frontend/editor-ui/src/app/composables/useWorkflowSaving.ts#L771-L844).

On the server, update and activation are distinct paths, with `versionId`, `activeVersionId` and checksum checks. Saving a draft and changing production activation are not inherently the same event, although particular calls can explicitly request publication. Manual execution also makes sure the relevant draft has been saved. [Workflow update](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/cli/src/workflows/workflow.service.ts#L391-L510), [activation](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/cli/src/workflows/workflow.service.ts#L906-L1018), [save before run](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/frontend/editor-ui/src/app/composables/useRunWorkflow.ts#L160-L190).

Live execution messages enter an event queue, then dispatch to handlers bound to the currently viewed document. `nodeExecuteAfterData` rejects messages from a different active execution before storing outputs. This guards against navigation and concurrent-run contamination. [Push dispatch](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/frontend/editor-ui/src/app/composables/usePushConnection/usePushConnection.ts#L40-L99), [execution identity check](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/frontend/editor-ui/src/app/composables/usePushConnection/handlers/nodeExecuteAfterData.ts#L11-L41).

Historic execution debugging can import output into the editor and pin inputs. It checks redaction/reveal permissions and asks before overwriting matching pins. The inspected UI gates Debug in editor through an enterprise feature flag. Ordinary node testing, data pinning and this historic-debug feature should not be conflated. [Historic debugging](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/frontend/editor-ui/src/features/execution/executions/composables/useExecutionDebugging.ts#L47-L150).

### Do not infer accessibility from the canvas dependency

The inspected n8n canvas explicitly disables Vue Flow's built-in keyboard accessibility and supplies its own interaction handling. Its details view also implements focus placement. This is evidence that keyboard behavior is application work, not a dependency checkbox. It does not establish an accessibility failure or compliance result. OpenPost should verify keyboard step insertion, movement, configuration, data mapping, undo and focus return in its own editor. [Canvas keyboard settings](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/frontend/editor-ui/src/features/workflows/canvas/components/Canvas.vue#L1914-L1918), [details focus handling](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/frontend/editor-ui/src/features/ndv/shared/views/NodeDetailsView.vue#L719-L744).

## n8n connector contracts and runtime

### Metadata, imperative actions and declarative routing

`INodeTypeDescription` combines versions, ports, credential requirements, properties, polling, webhooks, activation hooks and redaction metadata. `INodeProperties` includes defaults, conditional visibility, expression support, validation, resource locator modes and request routing. `INodeType` supplies distinct `execute`, `poll`, `trigger`, `webhook` and `supplyData` capabilities, plus editor discovery methods. A connector is therefore a small integration application, not a REST endpoint with a logo. [Description contract](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/workflow/src/interfaces.ts#L3099-L3144), [properties](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/workflow/src/interfaces.ts#L2171-L2209), [executable capabilities](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/workflow/src/interfaces.ts#L2559-L2615).

Imperative nodes implement `execute`. Declarative nodes attach request/response instructions to properties; the server supplies an execution adapter backed by `RoutingNode`. That adapter resolves inputs per item, combines request instructions, injects authentication, runs hooks, handles pagination and transforms results. Declarative hooks can still execute code. The npm node illustrates this: Get Metadata declares a GET route, while Get Versions includes a transformation of registry timestamps into sorted items. [Execution adapter](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/cli/src/node-types.ts#L95-L120), [routing construction](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/core/src/execution-engine/routing-node.ts#L139-L186), [routing hooks](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/core/src/execution-engine/routing-node.ts#L608-L650), [npm operations](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/nodes-base/nodes/Npm/PackageDescription.ts#L10-L102).

This supports shared metadata with dedicated handlers in OpenPost. It does not imply the Go engine should interpret arbitrary n8n request templates or bypass native services.

### Concrete GitHub and HTTP paths

GitHub owner/repository selectors support list, URL and name modes. List mode invokes authenticated search; URL mode extracts an identifier; manual entry remains available. The server receives node type/version, parameters, credentials, filter and pagination, checks credential access, builds a temporary execution context and invokes the named search method. The inspected GitHub repository search catches failures and returns an empty result, illustrating a UX weakness: provider errors should remain distinguishable from no matching resources. [Locator definitions](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/nodes-base/nodes/Github/Github.node.ts#L538-L660), [search implementation](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/nodes-base/nodes/Github/SearchFunctions.ts#L69-L133), [discovery authorization](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/cli/src/services/dynamic-node-parameters.service.ts#L73-L129), [method invocation](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/cli/src/services/dynamic-node-parameters.service.ts#L300-L321).

GitHub's imperative action node resolves parameters per input item, chooses token/App/OAuth authentication, calls the shared request helper and returns items with `pairedItem` provenance. GitHub Trigger is a separate implementation. Activation creates a signed repository webhook and records its ID and secret in node static data; conflict recovery verifies stored identity instead of adopting an unrelated webhook. Ingress verifies HMAC before emitting workflow data. Trigger registration has external effects and its own recovery lifecycle. [Action request helper](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/nodes-base/nodes/Github/GenericFunctions.ts#L16-L67), [action output](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/nodes-base/nodes/Github/Github.node.ts#L3205-L3237), [webhook lifecycle](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/nodes-base/nodes/Github/GithubTrigger.node.ts#L483-L615), [HMAC comparison](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/nodes-base/nodes/Github/GithubTriggerHelpers.ts#L40-L77).

HTTP Request retains older classes and maps several newer node versions to one implementation. A saved type version is a compatibility contract, not necessarily an immutable implementation artifact. The current implementation creates per-item request promises and collects them through `Promise.allSettled`; batching spaces starts and is not a global provider-rate guarantee. It sanitizes request details after completion because OAuth refresh may have changed credentials during the call. [Version map](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/nodes-base/nodes/HttpRequest/HttpRequest.node.ts#L8-L37), [dispatch](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/nodes-base/nodes/HttpRequest/V3/HttpRequestV3.node.ts#L735-L806), [results and redaction](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/nodes-base/nodes/HttpRequest/V3/HttpRequestV3.node.ts#L831-L875).

### Credential readiness is more than stored secrets

Credential types declare fields, inheritance, authentication, tests and supported nodes. Stored values are encrypted. Runtime lookup checks identity/type and usage policy before decryption, with additional dynamic-resolution behavior. Manual and production resolution can differ. [Credential contract](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/workflow/src/interfaces.ts#L417-L453), [encrypted storage](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/core/src/credentials.ts#L19-L66), [runtime lookup](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/cli/src/credentials-helper.ts#L330-L374), [dynamic resolution](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/cli/src/credentials-helper.ts#L551-L679).

A credential test's strength depends on its implementation. An explicit GitHub token test calls GET `/user`; an OAuth fallback in the generic tester can succeed merely because token data contains an access token. Connection present, token structurally valid and required operation permitted are different readiness states. [GitHub test](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/nodes-base/credentials/GithubApi.credentials.ts#L15-L53), [generic fallback](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/cli/src/services/credentials-tester.service.ts#L74-L131).

OAuth refresh coordinates by credential ID and re-reads stored tokens to notice another worker's refresh. Cross-process lease timeout can fall back to uncoordinated refresh. Single-use stream and multipart bodies are not resent after refresh. These details matter for media imports: replaying an authenticated request is not always possible even before considering the provider's write semantics. [Refresh reread](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/core/src/execution-engine/node-execution-context/utils/request-helpers/oauth.ts#L151-L195), [coordination fallback](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/core/src/execution-engine/node-execution-context/utils/request-helpers/oauth.ts#L296-L307), [non-replayable bodies](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/core/src/execution-engine/node-execution-context/utils/request-helpers/oauth.ts#L521-L542).

### The established engine runs batches with item lineage

The established engine is called v1 here because the inspected revision also contains an opt-in v2 path. v1 passes arrays of items through indexed ports. Each item can hold JSON, binary references, errors and `pairedItem` lineage. The engine maintains an execution stack, waiting inputs and per-node run history. A handler returning no output without waiting ends that branch; it is not necessarily a failed step. [Item fields](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/workflow/src/interfaces.ts#L1844-L1873), [execution loop](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/core/src/execution-engine/workflow-execute.ts#L2226-L2282), [branch completion](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/core/src/execution-engine/workflow-execute.ts#L2400-L2451).

One important coupling remains between layout and execution. When `settings.executionOrder === 'v1'`, the established engine sorts eligible downstream nodes by their stored canvas positions to execute the top-left node first. Moving nodes can therefore change branch order. OpenPost should make required order explicit in the executable document. This execution-order setting is distinct from the opt-in `engineType` discussed below. [Position-based scheduling](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/core/src/execution-engine/workflow-execute.ts#L2524-L2577).

Automatic item pairing is convenient but limited. It links a single input to outputs, aligns equal input/output counts by index, and can associate a many-to-one aggregation with only the first input. This is expression-navigation assistance rather than a complete causal record. OpenPost should carry explicit source, event, publication and iteration identities where attribution or duplicate prevention depends on them. [Pairing implementation](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/core/src/execution-engine/workflow-execute.ts#L3094-L3145).

### Definition snapshots, waits and recovery

Production lookup follows `workflow_published_version` to a history version; it does not simply execute the editable row. Execution persistence stores a workflow snapshot and version beside execution state. That protects inspection and resumption from later draft changes. It still does not freeze the installed connector binary forever. [Published lookup](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/cli/src/workflows/workflow-published-data.service.ts#L34-L100), [version selection](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/@n8n/db/src/repositories/workflow-published-version.repository.ts#L94-L128), [execution snapshot](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/cli/src/executions/execution-persistence.ts#L91-L142).

Time-only waits shorter than 65 seconds sleep in-process with cancellation. Longer or request-resumable waits persist `waitTill`, return the node to the execution stack and release execution. A leader polls persisted waits, installs timers, reloads the snapshot and claims the expected waiting execution before resuming. Competing resumes fail the guarded transition. [Wait split](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/core/src/execution-engine/node-execution-context/base-execute-context.ts#L135-L151), [threshold](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/workflow/src/constants.ts#L19), [suspension](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/core/src/execution-engine/workflow-execute.ts#L2453-L2463), [wait tracker](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/cli/src/wait-tracker.ts#L68-L174), [guarded resume](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/cli/src/active-executions.ts#L123-L147).

When a subworkflow waits, the parent records the child execution and parks separately. Completion patches the parent with child output before resuming it, rather than independently waking both on the same timer. A visual group cannot supply these semantics. [Parent suspension](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/core/src/execution-engine/node-execution-context/base-execute-context.ts#L154-L216), [parent result propagation](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/cli/src/wait-tracker.ts#L187-L229).

Queue mode uses Bull/Redis to dispatch execution IDs; workers load the saved state. ## Activepieces editor and pieces

### A structured document, rendered as a canvas

`FlowVersion` owns a trigger, schema version, connection references, notes and draft/locked state. Sequential actions use `nextAction`; loops own `firstLoopAction`; routers own ordered `children`; piece and code actions can own success/failure branches. The schema encodes branch ownership instead of persisting arbitrary React Flow edges. [Version schema](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/core/execution/src/lib/flows/flow-version.ts#L7-L27), [recursive actions](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/core/execution/src/lib/flows/actions/action.ts#L343-L415).

`buildFlowGraph` recursively creates display nodes, edges, loop returns and insertion controls. Horizontal layout transposes the computed vertical layout. React Flow provides rendering, selection and viewport controls; normal node connections and dragging are disabled. A separate drag layer moves steps between valid insertion locations. The connector between two boxes describes program structure rather than defining it. [Graph construction](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/web/src/app/builder/flow-canvas/utils/flow-canvas-utils.ts#L37-L183), [canvas configuration](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/web/src/app/builder/flow-canvas/index.tsx#L216-L248), [drag lifecycle](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/web/src/app/builder/flow-canvas/flow-drag-layer.tsx#L114-L195).

This makes a sequence editor and a canvas natural alternative views. Its cost is that a new control construct needs schema, mutation, layout, binding and execution support. Arbitrary joins do not become available merely because the renderer can draw another line.

### Semantic operations and save recovery

Editing uses named operations such as `ADD_ACTION`, `MOVE_ACTION`, `UPDATE_ACTION`, `DELETE_BRANCH` and `SET_SKIP_ACTION`. Insertion locations identify a parent and branch. Moving a step expands into operations that preserve its child structure. Shared operation application also normalizes piece versions and recomputes validity. [Operation contract](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/core/execution/src/lib/flows/operations/index.ts#L28-L55), [positions](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/core/execution/src/lib/flows/operations/index.ts#L107-L183), [move implementation](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/core/execution/src/lib/flows/operations/move-action.ts#L7-L38), [shared application](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/core/execution/src/lib/flows/operations/index.ts#L350-L434).

The Zustand store applies operations optimistically and serializes saves through a promise queue. Step changes debounce by step name, notes by note ID, while structural edits queue immediately. Successful responses reconcile server metadata without replacing every newer local edit. A failed operation logs the error and halts this queue; the queue itself has no restart method. Recovery after a failed optimistic save deserves an explicit design in OpenPost. [Save path](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/web/src/app/builder/state/flow-state.ts#L159-L259), [queue implementation](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/web/src/lib/promise-queue.ts#L3-L28).

Server mutations prepare and validate operations before applying them. Editing a locked version creates a draft. Publishing locks a version and updates `publishedVersionId` transactionally, then updates activation and caches. These are useful boundaries to retain. [Server validation](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/server/api/src/app/flows/flow-version/flow-version.service.ts#L343-L360), [draft creation](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/server/api/src/app/flows/flow/flow.service.ts#L987-L1045), [publishing](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/server/api/src/app/flows/flow/flow.service.ts#L480-L545).

The reviewed builder state and shortcut registry did not expose workflow-wide undo/redo. Text history and restoring a historical version are different operations. The inspected mutation contract also lacks an expected document revision. These bounded observations do not demonstrate an editing bug; they do mean that client-side serialization alone is not evidence of safe concurrent editing. [Shortcuts](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/web/src/app/builder/shortcuts.ts#L59-L139), [version restoration](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/server/api/src/app/flows/flow-version/flow-version.service.ts#L51-L79).

## Activepieces execution and recovery

### Sequential execution and distinct retry policies

The executor walks `nextAction`, dispatches by action type, handles success/failure branches and stops on non-running verdicts. Loops and router branches run serially, including all-matching branches. Piece execution resolves inputs, records censored values, validates/coerces properties and supplies services for files, connections, storage, nested flows and waitpoints. Workers provision exact pieces before invoking the engine. BullMQ queues work; the inspected queue default is two infrastructure attempts with exponential backoff starting at eight minutes. [Flow executor](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/server/engine/src/lib/handler/flow-executor.ts#L72-L164), [loops](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/server/engine/src/lib/handler/loop-executor.ts#L53-L85), [branches](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/server/engine/src/lib/handler/branch-execution.ts#L9-L43), [piece execution](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/server/engine/src/lib/handler/piece-executor.ts#L20-L148), [queue defaults](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/server/api/src/app/workers/job-queue/job-queue.ts#L163-L175).

Action retry is separate from queue retry. It reruns a failed action with exponential sleeps when enabled, without consulting the action's idempotency metadata in that helper. Retry from failure restores the original version and successful prior steps; retry on the latest version creates a new run with the old trigger output. Neither can infer whether a timed-out remote write already succeeded. [Action retry](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/server/engine/src/lib/helper/error-handling.ts#L6-L50), [run retry modes](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/server/api/src/app/flows/flow-run/flow-run-service.ts#L116-L208), [restoration](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/server/engine/src/lib/operations/flow.operation.ts#L260-L269).

### Durable waits handle early callbacks

An action creates a waitpoint tied to its execution path and requests suspension. The API stores a pending record and schedules its deadline. If the callback arrives while the run still says RUNNING, it marks the waitpoint completed. When PAUSED state arrives later, the system finds that completion and schedules resume. Per-run locks, transactional transitions and waitpoint-specific job IDs address duplicate and out-of-order signals. This is a particularly valuable implementation to study for approvals and publication-completion waits. [Waitpoint service](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/server/api/src/app/waitpoints/waitpoint-service.ts#L18-L159), [resume coordination](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/server/api/src/app/waitpoints/resume-service.ts#L28-L80), [job identity](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/server/api/src/app/waitpoints/resume-service.ts#L230-L240), [early callback recovery](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/server/api/src/app/flows/flow-run/flow-runs-queue.ts#L140-L148).

The Slack approval action illustrates the full cycle: create a waitpoint, send/update the approval message, pause, resume with the answer and update the message. For OpenPost, an approval should additionally name the exact content revision, destinations and authorized reviewer. [Slack approval](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/pieces/community/slack/src/lib/actions/request-approval-message.ts#L36-L140).

Recovery also depends on compressed execution snapshots. The progress reporter periodically uploads state and makes a final backup; resume downloads and parses it. Logs used for recovery cannot have the same retention contract as disposable debugging output. OpenPost should keep domain outcomes and active wait state durable independently of verbose run payloads. [Progress persistence](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/server/engine/src/lib/helper/flow-run-progress-reporter.ts#L93-L150), [resume loading](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/server/engine/src/lib/operations/flow.operation.ts#L226-L257).

### Trigger lifecycle and extension security

Triggers own enable/disable hooks, tests, event handling and optional handshake/renewal. GitHub's inspected registration helper creates a repository webhook and saves its remote ID for deletion, but sends no webhook secret in that helper. This is a bounded observation, not a full webhook security audit. The central `_dedupe_key` mechanism uses a 30-second Redis window scoped to workflow version. It is not permanent source-item identity or once-per-post deduplication. [Trigger SDK](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/pieces/framework/src/lib/trigger/trigger.ts#L41-L74), [GitHub registration](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/pieces/community/github/src/lib/trigger/register-trigger.ts#L31-L74), [dedupe lifetime](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/server/api/src/app/trigger/dedupe-service.ts#L6-L48).

Connections are validated and encrypted before storage. Worker reads derive scope from the engine principal, while enforcing the connection's piece binding is a separate optional check. Downloading/installing third-party pieces also entails cached dependency workspaces and exact package aliases. A permissive SDK does not remove the work of securing credential access or package execution. [Connection storage](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/server/api/src/app/app-connection/app-connection-service/app-connection-service.ts#L57-L118), [worker authorization](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/server/api/src/app/app-connection/app-connection-worker-controller.ts#L8-L44), [piece binding](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/server/engine/src/lib/piece-context/connection-resolver.ts#L55-L60), [package installation](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/server/sandbox/src/lib/cache/pieces/piece-installer.ts#L31-L143).

Process isolation and code isolation are separate choices. The sandbox can use Linux `isolate` or an ordinary fork; code can use a V8/Deno sandbox or unrestricted execution. The process sandbox shares networking, and the source describes STRICT SSRF protection as best-effort, with hard egress enforcement delegated to infrastructure. These mechanisms require a deployment-specific security assessment before hosting untrusted customer code. [Process selection and network boundary](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/server/sandbox/src/lib/create-sandbox-for-job.ts#L48-L91), [isolate configuration](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/server/sandbox/src/lib/sandbox/isolate.ts#L98-L134), [code modes](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/server/engine/src/lib/core/code/code-sandbox.ts#L23-L59).
## Licensing and practical reuse

n8n's root license is Sustainable Use License 1.0, with separate enterprise treatment for `.ee.` files/directories and original terms for third-party components. Its internal-business/non-commercial restrictions do not grant general reuse rights for a commercial hosted workflow product. The inspected workflow SDK and engine packages also declare `LicenseRef-n8n-sustainable-use`. Treat n8n as an architectural and behavioral reference for OpenPost unless separate rights are established. [Root license](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/LICENSE.md#L3-L35), [SDK declaration](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/@n8n/workflow-sdk/package.json#L115), [engine declaration](https://github.com/n8n-io/n8n/blob/2f2bac4645472e5efc72c4efedaadff6ef50348e/packages/@n8n/engine/package.json#L52).

Activepieces assigns MIT to ordinary repository content, with exceptions for `packages/ee/`, `packages/server/api/src/app/ee` and third-party components. The commercial paths include workflow publication approvals and piece visibility policies. Those publication approvals are different from an ordinary Slack approval action inside a run. Exact file provenance and dependencies matter before reuse. [Root license](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/LICENSE#L3-L17), [enterprise terms](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/ee/LICENSE#L6-L24), [publication approval owner](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/server/api/src/app/ee/flows/flow-approval/flow-publish-hook.ts#L9-L32), [piece visibility owner](https://github.com/activepieces/activepieces/blob/fa8d0c3aabfd1a44003e9536e08aced875cb90b7/packages/server/api/src/app/ee/pieces/filters/piece-filtering-utils.ts#L10-L46).

No upstream implementation was copied into OpenPost. Even permissively licensed pieces would not run natively in Go: their TypeScript context expects connection, storage, file, property-discovery and execution services. Adopting a piece runner would create a separate supported runtime, package lifecycle and security boundary. Reimplementing selected integrations against provider APIs and the native action contract is a different option. This decision should be made explicitly rather than hidden inside a promise to reuse a connector catalog.

## What current OpenPost changes about the handoff

### Keep four kinds of connector distinct

| Mechanism | Existing responsibility |
| --- | --- |
| Built-in provider adapter | Social publishing and authentication, with optional interfaces for comments, analytics and other capabilities. |
| Connector Protocol | An operator-run process can supply a publishing destination and reconcile its delivery. |
| `n8n-nodes-openpost` | A package inside n8n that invokes curated OpenPost REST operations. |
| Proposed native workflow connector | Would supply action/source metadata, configuration discovery, trigger lifecycle and execution in OpenPost. This general contract does not yet exist. |

`platform.Publisher` requires only publishing; the broader adapter and optional interfaces add distinct capabilities. Connector Protocol 1.0's current manifest validation is much narrower than an n8n node or Activepieces piece. It accepts preconfigured, text-only destinations. Its publisher already uses the provider-write fence and reconciliation. Turning that protocol into arbitrary workflow plugins would be a new protocol decision. [Provider interfaces](https://github.com/getopenpost/openpost/blob/24169ec9a29e1532fb0cac3c0341fec67ff3c385/apps/server/internal/platform/adapter.go#L420-L500), [connector manifest](https://github.com/getopenpost/openpost/blob/24169ec9a29e1532fb0cac3c0341fec67ff3c385/apps/server/internal/connectors/manifest.go#L77-L152), [connector publication](https://github.com/getopenpost/openpost/blob/24169ec9a29e1532fb0cac3c0341fec67ff3c385/apps/server/internal/connectors/publisher.go#L25-L98).

### Existing metadata is useful, but not a workflow engine

`automationcatalog` already owns access, adapter exposure, effect, retry, idempotency, pagination and selector metadata. Huma exports it through `x-openpost-automation`. It also participates in REST authorization, so changing its access classifications can change token permissions. Workflow exposure and permission policy must remain separate choices. [Catalog contract](https://github.com/getopenpost/openpost/blob/24169ec9a29e1532fb0cac3c0341fec67ff3c385/apps/server/internal/automationcatalog/catalog.go#L1-L79), [OpenAPI export](https://github.com/getopenpost/openpost/blob/24169ec9a29e1532fb0cac3c0341fec67ff3c385/apps/server/internal/api/config.go#L78-L100), [REST authorization](https://github.com/getopenpost/openpost/blob/24169ec9a29e1532fb0cac3c0341fec67ff3c385/apps/server/internal/api/middleware/auth.go#L75-L155).

The n8n generator combines this contract with a curated action list and rejects missing/disabled operations. The runtime maps n8n items into authenticated REST calls and returns linked outputs; resource pickers call native endpoints. This is a useful local example of adapter-specific presentation over shared contracts, without exposing every API endpoint as a node. [Generation](https://github.com/getopenpost/openpost/blob/24169ec9a29e1532fb0cac3c0341fec67ff3c385/scripts/generate-selected-automation-contract.mjs#L278-L337), [selected operations](https://github.com/getopenpost/openpost/blob/24169ec9a29e1532fb0cac3c0341fec67ff3c385/packages/n8n-nodes-openpost/docs/selected-contract-report.md#L1-L33), [runtime](https://github.com/getopenpost/openpost/blob/24169ec9a29e1532fb0cac3c0341fec67ff3c385/packages/n8n-nodes-openpost/nodes/OpenPost/v1/OpenPostV1.node.ts#L69-L165).

One concrete concern needs a separate focused reproduction. The default n8n write key is `n8n:${executionId}:${actionKey}:${itemIndex}`. It omits node identity and repeated-visit scope, so two same-action nodes at item zero in one run can produce the same key. Different request fingerprints should conflict; identical ones can replay an earlier result. This is a source finding, not a reproduced execution failure. It reinforces the need for stable logical step and iteration identity. [Key construction](https://github.com/getopenpost/openpost/blob/24169ec9a29e1532fb0cac3c0341fec67ff3c385/packages/n8n-nodes-openpost/nodes/OpenPost/v1/actions/mapper.ts#L140-L148), [replay checks](https://github.com/getopenpost/openpost/blob/24169ec9a29e1532fb0cac3c0341fec67ff3c385/apps/server/internal/idempotency/store.go#L79-L105).

### Several proposed foundations already exist

The transport-neutral `publications.Application` exists, with its concrete implementation still in handlers. The public interface omits stable command-idempotency inputs, but the implementation already has idempotent create, update, schedule, publish, cancel and retry variants. The integration task is to expose those guarantees appropriately. The default request-idempotency TTL is 24 hours; the builder's commit path already uses a durable expiry. Multi-day workflow effects need an explicit lifetime beyond disposable logs. [Application interface](https://github.com/getopenpost/openpost/blob/24169ec9a29e1532fb0cac3c0341fec67ff3c385/apps/server/internal/services/publications/contract.go#L349-L364), [idempotent creation](https://github.com/getopenpost/openpost/blob/24169ec9a29e1532fb0cac3c0341fec67ff3c385/apps/server/internal/api/handlers/publication_application.go#L194-L217), [idempotent scheduling](https://github.com/getopenpost/openpost/blob/24169ec9a29e1532fb0cac3c0341fec67ff3c385/apps/server/internal/api/handlers/publication_application.go#L687-L739), [default TTL](https://github.com/getopenpost/openpost/blob/24169ec9a29e1532fb0cac3c0341fec67ff3c385/apps/server/internal/idempotency/store.go#L20-L43), [durable build commit](https://github.com/getopenpost/openpost/blob/24169ec9a29e1532fb0cac3c0341fec67ff3c385/apps/server/internal/api/handlers/publication_application.go#L220-L253).

The handoff's reply inventory is incomplete. `POST /renditions/{id}/reply` already accepts content, parent ID, settings, media and optional `run_at`; it inserts a durable job and explicit authorization receipt in one transaction. Execution rechecks authority and uses the provider-write path. A workflow needs a transport-neutral, capability-aware, idempotent command with explicit root/last/selected-segment meaning. It should build on an audit of this route. [Reply admission](https://github.com/getopenpost/openpost/blob/24169ec9a29e1532fb0cac3c0341fec67ff3c385/apps/server/internal/api/handlers/publications.go#L1331-L1431), [reply execution](https://github.com/getopenpost/openpost/blob/24169ec9a29e1532fb0cac3c0341fec67ff3c385/apps/server/internal/services/publisher/publisher.go#L1081-L1135).

There is also `FirstCommentPoster` for LinkedIn, Facebook, Instagram and YouTube. Its current use is best-effort after parent publication, with lifecycle reporting and a direct provider call. That is a different guarantee from independently queued replies. Adding auto-plugs should reconcile these paths deliberately. [First-comment contract](https://github.com/getopenpost/openpost/blob/24169ec9a29e1532fb0cac3c0341fec67ff3c385/apps/server/internal/platform/first_comment.go#L13-L37), [best-effort implementation](https://github.com/getopenpost/openpost/blob/24169ec9a29e1532fb0cac3c0341fec67ff3c385/apps/server/internal/services/publisher/first_comment.go#L32-L80).

### Event admission and scheduling remain real gaps

The lifecycle recorder can insert an event and enqueue external-webhook work atomically, but still requires a publication ID. It is not a general workflow event bus. Moreover, support for a transaction does not mean every caller uses one: draft creation records lifecycle in its mutation transaction, while successful provider publication updates the rendition and then records lifecycle separately. A workflow trigger needs durable admission or reconciliation across that boundary. The next-slot endpoint calculates and returns a suggestion without reserving it. The handoff correctly identifies a need for atomic allocation-and-scheduling if workflows promise to take the next available slot. Whether occupancy should be workspace-wide or destination-specific remains a product decision. [Next-slot calculation](https://github.com/getopenpost/openpost/blob/24169ec9a29e1532fb0cac3c0341fec67ff3c385/apps/server/internal/api/handlers/posting_schedules.go#L586-L680).

### Reposts and publishing define the compatibility bar

Reposts already support inherited/off/custom settings, all/any thresholds, plateau checks, multiple targets and ordered stages relative to original publication time. The runtime snapshots rules, identifies provider operations by execution/stage, prohibits blind repost retry and separately checkpoints removal of a preceding repost. Those distinctions would need parity before replacing this engine. Missing metrics already fail enabled thresholds rather than becoming zero; a general wait-for-metrics result would still need freshness and availability information. ## Comparison and implications

This table summarizes the cited paths above. The last column contains recommendations, not approved requirements.

| Concern | n8n at the inspected revision | Activepieces at the inspected revision | OpenPost implication |
| --- | --- | --- | --- |
| Program model | General graph, typed ports, arrays of items | Recursive sequence with owned branches and loops | Decide composition semantics before canvas behavior. |
| Canvas | Vue Flow projection with application-owned mutations | React Flow projection with semantic insertion/movement | Keep the executable document independent of Svelte Flow. |
| Editing | Command history, serialized autosave, checksum conflict handling | Optimistic semantic operations and serialized saves; queue halts on failure | Design undo, save failures and concurrent editing separately. |
| Fields | Rich node properties, resource locators, custom controls | Piece properties, refreshers and dynamic schemas | Share field metadata and retain specialized native editors. |
| Data | Sample/declared schemas, expressions, item linking, pins | Path-aware data selector, sample outputs, typed whole-value references | Use immutable IDs and explicit missing/type errors. |
| Versions | Draft/published lookup and execution snapshots; node type versions | Draft/locked versions and exact piece versions | Version the definition, handler contract and dependency policy. |
| Testing | Partial runs, pins, explicit verification simulation and wire mocks | Test handlers default to real action handlers | Show whether a test reads, spends, writes or simulates. |
| Waiting | Snapshot/stack suspension, guarded resume, child-result propagation | Persistent waitpoints, early-callback handling and resume locks | Persist correlation and state before releasing a worker. |
| Retrying | Handler retries plus distinct queue/crash recovery | Action retry, infrastructure retry and run replay modes | Retry by operation policy and stable effect identity. |
| Credentials | Encrypted, scoped runtime resolution, connector-specific tests | Encrypted connections and engine-scoped reads | Recheck current authority and distinguish readiness states. |
| Extensibility | Executable node packages plus separate Code runners | Executable pieces plus process/code isolation modes | Native action extensibility does not require a package marketplace. |
| Reuse | Sustainable Use and enterprise restrictions | MIT core with commercial and third-party exceptions | Prefer behavioral lessons; audit exact provenance before code reuse. |

## How I would revise the provisional ideas

Retain the strongest invariants from the handoff: regular OpenPost publications, one behavior behind simple forms and advanced editing, immutable run definitions, durable waits, current authorization checks, inspectable outcomes and operation-specific recovery. Both upstream systems reinforce the importance of those concerns, while their implementation limits explain why they must be specified rather than assumed.

Reopen these choices before treating the handoff as a design:

1. **Choose structured composition or a general graph.** My starting recommendation is structured steps, branches and loops. Test whether the actual workflows need arbitrary cross-links or parallel joins before accepting their validation and recovery cost.
2. **Separate a useful first workflow from repost migration.** A source-to-reviewed-draft flow could validate discovery, bindings and native authoring while existing reposts continue. A follow-up flow tests durable timing and provider outcomes. Neither requires immediately replacing every repost setting.
3. **Choose a small action vocabulary from complete journeys.** The two pasted catalogues disagree about what is Core. Avoid making the entire list a first release or counting each AI prompt preset as a distinct execution system.
4. **Specify typed values before choosing CEL or another expression language.** Required behavior includes literals, references, optional values, arrays, coercion, missing-data errors, execution-path visibility and bounded evaluation. The final language should satisfy that contract and support useful editor previews.
5. **Define version compatibility beyond a graph snapshot.** Saved node versions need supported implementations, upgrade behavior and dependency retention. Pinning a JSON type number alone cannot guarantee old code remains executable.
6. **Use existing commands, with suitable identities and lifetimes.** Expose publication idempotency and reply services, audit lifecycle admission, and define an effect key containing run, logical step and execution scope. Preserve its identity across retries and its receipt across long waits.
7. **Define safe tests as a real execution mode.** Preview should expose planned effects without dispatching them. Live tests must identify actual external calls and writes. Production cursors, dedupe guards and published content should not change incidentally during simulation.
8. **Keep connector adoption and untrusted code as separate decisions.** A native GitHub release source and a community TypeScript package runner have different implementation and operational costs. The latter is not a prerequisite for a useful workflow editor.
9. **Treat no-Redis/no-Node as a starting deployment preference, not a research conclusion.** The Go/database path fits current OpenPost. Worker fairness, large payloads and code execution require measurement and explicit bounds before a permanent deployment constraint is justified.
10. **Leave provider and model choices open.** OpenRouter, Jev, exact connector order and automatic DM replies require their own capability, permission and product evidence. This investigation did not verify those provider claims in the attachments.

## The next useful validation

Before implementing a broad engine, specify and prototype two end-to-end examples using the same draft model:

- A published rendition waits until a deadline, checks a fresh metric observation and creates one prepared reply through the existing authorized path.
- A GitHub release or content-source item produces an OpenPost draft, receives approval for the exact revision and schedules it through native commands.

Use these to settle the editor model, action contract, test behavior and execution identities. An implementation proof should then exercise duplicate event admission, edits during a wait, an approval arriving before suspension, revoked authority, an ambiguous provider response, missing field data, and a restart between persistence and queue wakeup. These are proposed acceptance cases, not tests executed by this research.

Keep the first prototype small enough to compare a sequence view and a canvas without changing execution semantics. Prove binding and run inspection alongside the boxes and lines. Defer the exact database table split and migration schedule until these contracts are clear.
