# Deployable Inventory

Read this inventory before changing runtime configuration, release workflows, or revision evidence. A successful build proves only that an artifact was built. Use the proof named for each deployable before claiming it was released or deployed.

| Deployable                  | Configuration owner                                                                                                                                                                                                                                                                                                                | Release path                                                                                                                                                                                                                         | Revision proof                                                                                                                                                                                                                                                                          |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Server and embedded web app | Bootstrap and data-plane values come from environment variables or their `_FILE` forms through `apps/server/internal/config/config.go`. Admin-managed settings are declared in `apps/server/internal/config/managed.go` and stored through `apps/server/internal/services/instancesettings/service.go`.                            | Tag CI builds and scans `deploy/docker/Dockerfile`, retaining its registry digest as an Actions artifact. The release workflow promotes that digest, deploys it, and uploads `openpost-server-*` binaries built from the tagged SHA. | The release workflow downloads the digest from successful tag CI and checks the image OCI version and revision labels. The image smoke test and production check require matching `/api/v1/version` and ready `/api/v1/ready`. Standalone binaries embed the tag and SHA.               |
| Marketing site              | Source and build configuration live under `apps/marketing/`, including `apps/marketing/vite.config.ts`. The external runtime owner is the Cloudflare Pages project `openpost-marketing`.                                                                                                                                           | The Pages Git integration builds clean `main` to `apps/marketing/dist`. CI retains a build artifact for verification but does not deploy it.                                                                                         | Run the marketing build, then `scripts/public-deployment-proof.mjs prove` as described in `docs/operations/cloudflare-edge-plan.md`. It requires the local full SHA, the Pages deployment full SHA, and the live host to agree.                                                         |
| Documentation site          | Source and build configuration live under `apps/docs/`, including `apps/docs/.vitepress/config.ts`. The external runtime owner is the Cloudflare Pages project `openpost-docs`.                                                                                                                                                    | The Pages Git integration builds clean `main` to `apps/docs/.vitepress/dist`. CI retains a build artifact for verification but does not deploy it.                                                                                   | Run the documentation build, then the same public deployment proof. It requires the local full SHA, the Pages deployment full SHA, and the live host to agree.                                                                                                                          |
| Android app                 | Release name and code live in `apps/mobile/app.json` and `apps/mobile/package.json`. Native persistence belongs in `apps/mobile/app.json` or `apps/mobile/plugins/`. Per-install server and token state live in `apps/mobile/src/lib/server.ts` and `apps/mobile/src/lib/api/token-store.ts`. GitHub owns release signing secrets. | CI builds the unsigned APK and records its SHA-256. The release workflow checks that the mobile version advances, downloads the APK from successful tag CI, verifies the checksum, signs it, and uploads `openpost-app-android.apk`. | `scripts/mobile-release.mjs` checks Expo and package version consistency and increasing Android version codes. The checksum verifies the unsigned artifact; `apksigner verify` verifies the signed APK. The source revision belongs to the CI run.                                      |
| CLI and MCP proxy           | Profiles and endpoint precedence live in `apps/cli/internal/config/config.go`. Tokens live behind `apps/cli/internal/auth/token_store.go`, never in the profile file.                                                                                                                                                              | The tag workflow builds `openpost-cli-*` and `openpost-mcp-*` for the release matrix and uploads them to the GitHub release.                                                                                                         | The binaries embed and print the release tag. The GitHub release tag identifies the source SHA, but the CLI and MCP binaries do not independently embed the full SHA or publish a checksum manifest. Do not claim stronger executable-level revision proof.                             |
| n8n package                 | Package identity and version live in `packages/n8n-nodes-openpost/package.json`. User-entered endpoint and token fields live in `packages/n8n-nodes-openpost/credentials/OpenPostApi.credentials.ts`. npm trusted-publisher configuration is external.                                                                             | After the exact server revision is live, the tag workflow packs and publishes `@getopenpost/n8n-nodes-openpost` through trusted publishing. Follow `docs/agents/n8n-package-release.md`.                                             | `scripts/n8n-package-release.mjs` matches the packed tarball integrity to npm. `scripts/verify-published-n8n-package.mjs` checks registry integrity, npm signatures, and a clean install. npm provenance records the workflow source. The package SemVer is independent of the app tag. |

Keep external deployment records outside the repository. Do not put Cloudflare responses, credentials, signing material, or operator evidence in Git.
